### 2. 问题 ②：Miuix 表单弹窗「输入框与按钮零间距」

**根因（上游源码定位，pinned tag `v0.9.4-rc01`）**：
`miuix-ui/src/commonMain/kotlin/top/yukonga/miuix/kmp/layout/DialogContentLayout.kt` 里
`DialogContent` 的布局是

```
Box(imePadding + navigationBarsPadding + captionBarPadding, …) {
    Column(contentModifier.align(BottomCenter | Center)) {   // ← 没有 verticalArrangement
        title?.let   { Text(Modifier.padding(bottom = 12.dp), …) }
        summary?.let { Text(Modifier.padding(bottom = 12.dp), …) }
        content()                                            // ← 我们的 content 直接接在后面
    }
}
```

即：**库的弹窗根 Column 不带任何间距**，留白只由 title / summary 各自的 `padding(bottom = 12.dp)` 提供。
`AppFormDialog.kt` 的 Miuix 分支此前把「字段 `Column(spacedBy(12.dp))`」和「按钮 `Row(spacedBy(12.dp))`」
写成 content 里的**两个平级节点** → 两者之间 0dp → 输入框下边与按钮上边重合。

**修法（照上游示例与本仓既有先例，不自创数值）**：

- 上游示例 `example/shared/src/commonMain/kotlin/component/DialogSection.kt:351`：弹窗 content 内堆叠多个元素的标准写法是**单一 `Column(verticalArrangement = Arrangement.spacedBy(12.dp))`**；
- 本仓同形态弹窗 `AppDialogs.kt`（批量修改存放位置）：单一 `Column(spacedBy(12.dp))` + 按钮 `Row(Modifier.padding(top = 8.dp))` → 合计 20dp；
- 本仓 `SettingsScreen.kt` 坚果云 Miuix 弹窗：单一 `Column(spacedBy(12.dp))` + 按钮区前 `Spacer(Modifier.height(4.dp))` → 合计 16dp（注释原话「按钮区与表单区之间额外留白」）。

采用 `AppDialogs.kt` 那套（12 + 8 = 20dp）：它与 `AppFormDialog` 同在组件层、按钮行形态完全相同
（`MiuixTextButton` × 2，各 `weight(1f)`），是最近的结构孪生。

### 3. 问题 ①：切换输入框时「键盘 + 弹窗弹一下」——机制分析与方案取舍（本轮**未改代码**）

**机制**（两套主题共用同一个下游原因）：弹窗位置是 IME inset 的函数，inset 只要在焦点切换的瞬间掉到 0 再回来，
弹窗就会「掉下去再弹上来」。

- MD3 侧：`AlertDialog` 是独立浮动窗口，`decorFitsSystemWindows = false` + `Modifier.imePadding()`（⚠️⑧ 那轮的修法），
  弹窗在**剩余空间里居中** → inset 归零 = 可用高度变大 = 弹窗下移，inset 回来 = 弹窗上移；
- Miuix 侧：库的 `DialogContent` 根 Box 自带 `.imePadding()`，手机竖屏下弹窗 `Alignment.BottomCenter` **底部贴合** →
  inset 归零 = 弹窗落到屏幕底、inset 回来 = 弹窗整体抬升。

`imePadding()` 是**逐帧跟随** `WindowInsets.ime` 的（Android 侧由 `WindowInsetsAnimation` 驱动），所以「弹一下」不是动画写错，
而是 inset 本身出现了一次瞬时下陷。最可能的诱因：焦点从一个输入框移到另一个时 Compose 调 `restartInput`，
若两框 `inputType` 不同（坚果云：`Text` → `Password`；编辑页多处 `KeyboardType.Number`），输入法会重启输入视图，
期间 IME 短暂报告不可见。**此诱因尚未在真机上确认**（见下「待确认」）。

**已否决 / 已排除的方案**：

| 方案 | 结论 |
|---|---|
| 去掉密码框的 `KeyboardType.Password`，让两框 `inputType` 一致从而不触发 IME 重启 | **否决**：这是隐私回退 —— 少了 `TYPE_TEXT_VARIATION_PASSWORD` 后输入法可学习/联想密码内容（`PasswordVisualTransformation` 只遮蔽显示，不给这个标志） |
| Miuix 侧传 `defaultWindowInsetsPadding = false`，自己接管 insets 做「保持上一次非零 IME 高度」 | **暂不做**：那个开关同时关掉库的 `navigationBarsPadding()` / `captionBarPadding()`，弹窗底边会掉到导航栏/手势条下面（圆角被压在手势条后），是所有 Miuix 弹窗的视觉回退，代价大于收益；`MiuixDialog.kt` 的 KDoc 里已写明不要传 |
| 给弹窗换成固定高度 / 关掉 `imePadding` | **否决**：会让键盘盖住按钮，正是 ⚠️⑧ 修掉的问题（用户已真机验证通过，不能倒退） |

**当前倾向的方案（待诊断确认后实施）**：MD3 侧做「IME inset 粘性保持」—— inset 掉到 0 时，若弹窗内仍有输入框持有焦点，
则保持上一次的非零值 ~200–250ms 再释放；期间 inset 回来就完全不动（焦点切换 = 零位移），
真的是收起键盘则只多 ~250ms 才落回居中。Miuix 侧受库结构限制（`imePadding` 在库内部、开关是全局的），
应用层没有干净的改法，可能需要给上游提 issue；若诊断显示诱因只在 `inputType` 变化，则 Miuix 侧的坚果云弹窗
还要在「隐私」与「流畅」之间由用户定一次方向。

**待确认（已在本轮向用户提问）**：
1. 在「分类管理」添加弹窗里，从「名称」切到「Emoji」（两个都是普通文本框、`inputType` 相同）会不会也弹一下？→ 判定诱因是「仅 `inputType` 变化」还是「任何焦点切换」；
2. 弹的时候键盘本身是整个消失再出现（输入法面板/候选栏闪一下），还是键盘一直显示、只有弹窗上下跳？→ 判定应用层能否根治（输入法窗口重启不在应用控制范围内）。

### 4. 新增静态守卫 `MiuixDialogContentTest`（单测 117 → 119 例）

问题 ② 这类缺陷的特点是**编译期完全静默**：间距为 0 不是错误，ktlint / detekt / lint 都不会响，
只有真机能发现 —— 与 `ImeHandlingTest` 拦的「键盘盖住按钮」同一档。所以照仓库既有做法补一条读源码的 JVM 单测。

**守卫口径**：

1. 每个 `MiuixDialog(…)` 调用点的尾随 lambda 里，**顶层语句必须恰好 1 条**；
2. 扫到的调用点数不得少于 `ExpectedCallSites = 8`（2026-09-17 实测：`AppDialogs` 1 + `AppConfirmDialog` 1 +
   `AppFormDialog` 1 + `AppOptionDialog` 1 + `SettingsScreen` 4）—— 解析器或源码布局变了会让守卫**空转**，
   而空转比没有守卫更糟，故宁可在这里响一次（与 `tools/ci-gates.sh` 的 `detekt_selftest` 同思路）。

**实现**：一个小型 Kotlin 词法状态机（`Walker`，约 90 行）判定「最外层代码语境且括号/花括号深度为 0」，
需要正确跳过：字符串、原始字符串 `"""`、**字符串模板 `${…}`**、字符字面量、行注释、**可嵌套的**块注释。
写的时候踩到两个坑，都记在这里以免下次重踩：

- **模板帧会被误判成「括号已配对」**：`${…}` 推入的代码帧 `paren` 也是 0，配对函数若只看栈顶帧就会在模板第一个字符处提前返回
  （症状：`AppDialogs.kt` 的 `summary = "已选 ${selectedIds.size} 件…"` 让整段扫描报「无尾随 lambda」）。修法：要求**回到最外层帧**（栈深 1）才判定配对完成；
- **模板的收尾符是 `}` 不是 `{`**：pop 挂错字符会让模板帧永远弹不出去、括号深度变成 -1；
- **字符字面量必须整体跳过**：`'"'` 会让状态机以为字符串从此处开始，把后面几十行吞掉；`'{'` 会被当成真的花括号。
  （这条在写守卫时顺手补上：本次扫描的 5 个文件里暂时没有字符字面量，但 CSV 导出那类文件里 `'"'` / `','` 很常见，将来弹窗文件里出现一个就会误判。）

**有效性验证（本地无 JDK，只能靠这一步兜住「守卫是否真的会响」）**：算法先用 Python 实现同一套状态机，
在真源码上跑通 —— 当前 8 个调用点全部判为单一根节点；把 `AppFormDialog.kt` 换回**修复前**（`git show HEAD~1:`）的版本，
被准确判为「2 个顶层节点：`Column(…)` + `Row(…)`」。Kotlin 版落盘后再用同一个 Python 解析器跑测试文件里的两段 canary 源码，
结论与 `assertEquals(1, …)` / `assertEquals(2, …)` 一致（含带字符字面量与字符串模板的正例）。
测试文件本身也过了机械预检：栈终态 `code 0/0`（括号完全配对）、无行尾空格、末尾单个换行、无连续空行、无 `}` 前空行、无通配 import。

**登记位点**（守卫存在但没人知道 = 没有守卫）：`docs/MIUIX_UPGRADE.md` §2 第 8 条 + §3 坑表 + 升级检查清单、
