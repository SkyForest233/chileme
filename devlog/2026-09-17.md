### 3. 问题 ①：诊断答案与机制结论

**用户真机答复（2026-09-17）**：

1. 「分类管理」弹窗里从「名称」切到「Emoji」（两个都是普通文本框、`inputType` 相同）**也会弹** →
   诱因**不是** `keyboardOptions`/`inputType` 变化，而是**焦点切换本身**；
2. 弹的时候**键盘整个消失再出现**（输入法面板会闪） → 是输入法窗口重启，不是单纯的 inset 抖动；
3. 补充观察：「输入法和弹窗都会一起很快地上下移动，Miuix 的弹窗贴底所以动的幅度特别大」，
   并要求先查 miuix-skill 有没有对应能力，**没有就只修 MD3**。

**机制**：弹窗位置是 IME inset 的函数，焦点切换触发 `restartInput` → 输入法窗口重建 → `WindowInsets.ime`
瞬时归零 → 两侧弹窗都动，但幅度不同，正好解释了用户的观察：

- **MD3**：弹窗是独立浮动窗口、由窗口管理器**居中**，`imePadding()` 让它在「屏幕减掉键盘」的剩余空间里居中 →
  inset 归零 = 可用高度变大 = 弹窗下坠约 **ime/2**；
- **Miuix**：库的根 Box 自带 `.imePadding()`，手机竖屏下弹窗 `Alignment.BottomCenter` **底部贴合** →
  inset 归零 = 弹窗整体落到屏幕底 = 位移 **整个 ime 高度**（约为 MD3 的两倍，故「幅度特别大」）。

`imePadding()` 是逐帧跟随 `WindowInsets.ime` 的（Android 侧由 `WindowInsetsAnimation` 驱动），所以「弹一下」不是动画写错，
而是 inset 本身出现了一次瞬时下陷。

**Miuix 侧查证结论（上游 pinned tag v0.9.4-rc01 + `.claude/skills/miuix` 都查了）**：

- 全库只有两处用到 ime：`layout/DialogContentLayout.kt` 的 `.imePadding()`，以及「弹窗关闭时 `keyboardController.hide()`」
  （`DialogContentLayout` 与 `utils/MiuixPopupUtils.kt:332`）。**没有任何 IME 平滑/粘性/保持能力**；
- `WindowDialog` 公开的唯一相关开关是 `defaultWindowInsetsPadding: Boolean = true`，而它是**三件套一起关**
  （`.imePadding().navigationBarsPadding().captionBarPadding()`）：关掉后弹窗底边掉到导航栏/手势条下面、
  squircle 圆角被压住，是**所有** Miuix 弹窗的视觉回退，代价大于收益；
- `.claude/skills/miuix` 里也没有：`overlays-and-windows.md` 全篇无 inset/IME 段落；
  `release-v0.9.4-rc01.md:111` 提到的 "search-bar inset timing" 被明确标注为 **Example-only、不是库的公开 API**，
  且同一句嘱咐「不要照抄 Example-only helper」。

→ 按用户决定：**Miuix 侧不动，只修 MD3**。要根治 Miuix 侧只能上游支持（可考虑给 `compose-miuix-ui/miuix` 提 issue，
建议内容：`DialogContent` 的 IME 避让做成可插拔，或对 inset 归零加一个短窗口的保持）。

**已否决的方案**：

| 方案 | 结论 |
|---|---|
| 去掉密码框的 `KeyboardType.Password`，让两框 `inputType` 一致以免触发 IME 重启 | **否决且已无必要**：隐私回退（少了 `TYPE_TEXT_VARIATION_PASSWORD`，输入法可学习/联想密码；`PasswordVisualTransformation` 只遮蔽显示、不给这个标志）；且诊断 ① 表明类型相同也会弹，改它没用 |
| Miuix 侧传 `defaultWindowInsetsPadding = false` 自行接管 insets | **否决**：见上，会连带丢掉导航栏/字幕栏避让 |
| 关掉弹窗的 `imePadding` | **否决**：键盘会盖住按钮，正是 ⚠️⑧ 修掉、用户已真机验证通过的问题，不能倒退 |
| 靠「弹窗内是否还有输入框持有焦点」区分「瞬时塌陷」与「真收起键盘」 | **否决**：Android 上用返回键收起键盘时**焦点仍留在输入框**，这个信号区分不了两种情况，会导致弹窗永远悬在半空 |

### 4. 问题 ① 的实施：`stickyImePadding()`（MD3 侧，待真机复测）

新增 `ui/components/app/AppIme.kt`（85 行，1 个公开 composable）：

```kotlin
LaunchedEffect(imeBottom) {
    val target = imeBottom
    if (target > held.value) held.snapTo(target)                        // 升起：逐帧跟随，与系统动画同步
    else if (target == 0f) { delay(holdMillis); held.animateTo(0f, tween(releaseMillis)) }   // 归零：先按住
    else held.animateTo(target, tween(releaseMillis))                    // 变矮但没收起（换输入法/分屏）：平滑跟随
}
return Modifier.padding(start = …, end = …, bottom = with(density) { held.value.toDp() })
```

- **焦点切换（inset 塌陷后回来）**：塌陷期间 `held` 保持在原值不动，inset 回来时 `snapTo` 到同一个值 →
  **弹窗零位移**，这是本次修复的全部目标；
- **真的收起键盘**：按住 `holdMillis`（默认 **300ms**，两个真机可调参数之一）后，用 `releaseMillis`（默认 **220ms**）
  平滑落回居中，不是硬跳。弹窗内点「取消 / 确定」关闭时看不出来（弹窗自己正在消失）；
  用返回键收键盘时，弹窗会晚 300ms 才开始落回 —— 这是**刻意接受的代价**，因为塌陷时长（输入法窗口重建）
  实测口径是「整个消失再出现」，短于 300ms 的保持挡不住它；
- **与 `imePadding()` 的两点差异**（都写进 KDoc）：① inset 变小时不立即跟随；② 只补 bottom + start/end 三段 padding、
  **不消费 insets**（`imePadding()` 会消费）—— 弹窗内容里没有第二个避让位点，故不会双重 padding；
  左右两段直接透传当前 inset，横屏侧挂输入法不会比现状差。

**接入点（三处，正是 `ImeHandlingTest` 第 3 条点名的三个文件）**：`AppFormDialog.kt`（分类名 + Emoji / 添加位置）、
`AppDialogs.kt`（批量移动存放位置）、`SettingsScreen.kt`（坚果云账号 + 应用密码），
均由 `modifier = Modifier.imePadding()` 改成 `modifier = stickyImePadding()`，`decorFitsSystemWindows = false` 保持不变。
三处各删掉一个不再使用的 `imePadding` import（`AppFormDialog` 与 `AppIme` 同包，不需要新 import；另两处补 import）。

**刻意不扩大到屏幕级**：`AppScaffold(modifier = Modifier.imePadding())` 的三个输入屏（编辑页 / 列表页 / 归档页）不改 ——
屏幕内容高、下坠幅度小得多，用户也没报；改它要动 `ImeHandlingTest` 第 1 条整份屏幕清单，风险与收益不成比例。
（编辑页确实有 `KeyboardType.Number` 的多字段切换，若用户日后报同样症状，把同一助手接过去即可，已登记为待办。）

**守卫同轮改**（`ImeHandlingTest`，与它守的结构在同一个提交里）：

### 5. 新增静态守卫 `MiuixDialogContentTest`（单测 117 → 119 例）—— 以及它连红两次的真因

问题 ② 这类缺陷**编译期完全静默**（间距为 0 不是错误，ktlint / detekt / lint 都不响），只有真机能发现，
与 `ImeHandlingTest` 拦的「键盘盖住按钮」同一档，故照仓库既有做法补一条读源码的 JVM 单测。

**守卫口径**：① 每个能解析出尾随 lambda 的 `MiuixDialog(…)` 调用点，content 的顶层语句必须**恰好 1 条**；
② 成功解析的调用点数不得少于 `ExpectedParsedSites = 8`（实测：`AppDialogs` 1 + `AppConfirmDialog` 1 +
`AppFormDialog` 1 + `AppOptionDialog` 1 + `SettingsScreen` 4）。解析不出来的调用点**不算违规**，
但会让这个计数掉下来 —— 于是「解析器失效」与「弹窗被删/改用具名参数」都会在第 ② 条上响，守卫不会静默空转
（与 `tools/ci-gates.sh` 的 `detekt_selftest` 同思路）。

**实现**：一个小型 Kotlin 词法状态机（`Walker`），需正确跳过字符串、原始字符串、字符串模板 `${…}`、
字符字面量、行注释、**可嵌套的**块注释。开发中踩到并修掉的坑，逐条记下：

1. **模板帧会被误判成「括号已配对」**：`${…}` 推入的代码帧 `paren` 也是 0，配对函数只看栈顶帧就会在模板第一个字符处提前返回
   （症状：`AppDialogs.kt` 的 `summary = "已选 ${selectedIds.size} 件…"` 让整段扫描报「无尾随 lambda」）。修法：要求**回到最外层帧**才判定配对完成；
2. **模板的收尾符是 `}` 不是 `{`**：pop 挂错字符会让模板帧永远弹不出去、括号深度变负；
3. **字符字面量必须整体跳过**：`'"'` 会让状态机以为字符串从此开始、把后面几十行吞掉，`'{'` 会被当成真花括号
   （本次扫描的 5 个文件暂时没有字符字面量，但 CSV 导出那类文件里 `'"'` / `','` 很常见，将来弹窗文件里出现一个就会误判）；
4. **`matchBrace` / `matchParen` 的 off-by-one（本轮 CI 连红两次的真因）**：循环条件是 `w.i < src.length && 深度 != 0`，
   退出后却用 `if (w.i < src.length)` 判成功 —— 当配对花括号**正好是最后一个字符**时 `w.i == src.length`，
   于是「找到了」被误判成「没找到」返回 −1。真源码里弹窗后面总还有代码，所以 8 处扫描一直不发作
   （**这也是本地 Python 复验没抓到它的原因：我拿真源码验，没验「以 `}` 结尾」的输入**）；
   而两段 canary 的文本正好以 `}` 结尾 → 旧写法 `substring(brace + 1, -1)` 直接抛
   `StringIndexOutOfBoundsException` → 测试 ERROR。修法：退出循环后**再判一次深度**（`rootParen()`/`rootBrace()`
   在 `i == length` 时依然可读、不越界），不再用位置判断；
5. **在 KDoc 里写出块注释定界符本身 → 注释自己配不平（本轮差点又一次 CI 红，被本地预检挡下）**：给
   `ImeHandlingTest.codeOnly()` 写「已知局限」时，为了说清那个 MIME 通配符，KDoc 里直接把两个定界符写了出来，
   结果该 KDoc 内出现 2 次「斜杠星号」、只有 1 次「星号斜杠」。**Kotlin 的块注释是可嵌套的**，多出来的那一次会让
   注释一路吃到文件末尾 → 编译失败。修法：KDoc 改用中文描述这两个符号（并注明为何不写出来）；
   `//` 行注释里的同样写法无害（行注释不嵌套），予以保留。
   **抓住它靠的正是那份词法状态机**：预检脚本跑完发现 `ImeHandlingTest.kt` 的栈终态是 `frames=2 / paren=-1 / brace=-1`，
   而其余文件都是 `1 / 0 / 0` —— 栈回不到最外层就等于「有东西没配平」。这条比 ktlint/detekt 更早发现问题，
   也再次说明：**守卫用的词法器顺手就是最好的本地编译预检**（沙箱无 JDK，CI 是唯一编译器）。

## ⚠️ 本轮新发现（此前任何文档都没登记）

### `ImeHandlingTest.codeOnly()` 的块注释剥离不认字符串字面量

`codeOnly()` 用 `Regex("/\\*.*?\\*/", DOT_MATCHES_ALL)` 剥块注释。`SettingsScreen.kt:379` 有
`importLauncher.launch(arrayOf("application/json", "text/plain", "*/*"))` —— MIME 通配符 `"*/*"` 里的 `/*`

（坚果云弹窗那处键盘避让就在被吞范围里）。

- 后果分两面：计数偏低会**假失败**（会响，能发现）；而 `assertFalse` 类断言会变**空转**（不响，危险）；
- 影响面已量清：只有 `SettingsScreen.kt` 命中这个模式，而它**不在**第 2 条的 `chromeFiles` / `navBarFiles` 清单里，
  第 1 条与第 3 条前半用的是**原文**匹配 → 现有断言今天都还成立，没有一条正在空转；
- 本轮处置：第 3 条新增的那半**刻意不用 `codeOnly()`**，改匹配完整赋值形态

  既精确又绕开该坑；坑本身写进了 `codeOnly()` 的 KDoc；

## 💡 决策记录

- **为什么问题 ② 直接修、问题 ① 先问再修**：② 的根因可以在上游源码里逐行指认，修法是照抄上游示例与本仓既有先例，
  零行为风险；① 的修法要动 IME 处理，而那正是 ⚠️⑧ 刚被用户真机验证通过的区域 —— 没有诊断数据就改，
  可能既没解决问题、又把已验证的行为改坏。两个诊断问题用户在真机前 30 秒就能答，成本远低于一轮 CI + 复测。
  事后看这一步是值的：诊断 ① 直接否决了「统一 `inputType`」这条本来排在最前面的思路（类型相同也会弹）。
- **为什么间距数值定为 20dp 而不是自己挑一个好看的**：Miuix 相关修复要遵循上游/库约定而不是发明。
  上游示例给的是「单一 Column + `spacedBy(12.dp)`」，本仓两个同形态弹窗分别给 16dp / 20dp；选 20dp 是因为
  `AppDialogs.kt` 与本组件同层、按钮行形态完全一致。数值来源全部可指认，日后有人问「为什么是 20」有答案。
- **为什么 Miuix 侧选择「不修」而不是「接管 insets」**：接管要把 `defaultWindowInsetsPadding = false`，
  而它是三件套开关 —— 弹窗底边会掉到导航栏/手势条下面、squircle 圆角被压住，这是**所有** Miuix 弹窗的视觉回退，
  用「一个弹窗不弹一下」换「所有弹窗底边错位」不划算。已查证上游无任何 IME 平滑能力，故只能等上游；
  用户 2026-09-17 拍板「没有的话只修复 MD3 的」。
- **为什么粘性避让选「时间窗」而不是「焦点信号」**：直觉方案是「弹窗内还有输入框持有焦点就保持住 padding」，
  但 Android 上用返回键收起键盘时**焦点仍留在输入框**，这个信号区分不了「瞬时塌陷」与「真的收起」，
  会让弹窗永远悬在半空。时间窗（按住 300ms 再平滑落回）是唯一能同时满足两种情况的机制，
  代价是收起键盘时多 300ms —— 而弹窗内的收起路径通常是「点取消/确定」，那时弹窗自己正在消失，看不出来。
- **为什么把两个时长做成带默认值的参数**：塌陷时长取决于输入法实现（本机是「整个消失再出现」），
  沙箱里测不到、只能真机调。写成参数 + 在 KDoc 里注明「真机可调」，用户复测后一句话就能改，不用重读实现。
- **为什么把「本地词法预检」提升为提交前的固定动作**：本轮 4 次 CI 里 2 次是红的 —— detekt 那次本地确实无从发现
  （要跑真 detekt），但 off-by-one 与「KDoc 配不平」这两类**都能在没有 JDK 的情况下用词法状态机提前抓到**，
  判据只有一条：跑完整份文件后栈必须回到最外层（`frames == 1 && paren == 0 && brace == 0`）。
  已并入每轮提交前的机械预检清单（配平 / 行尾空格 / 文件末尾 / 连续空行 / `}` 前空行 / 未使用 import）。
- **为什么守卫的解析失败改成「计数下降」而不是「硬断言失败」**：硬断言在解析器有边界 bug 时会把 CI 卡死在
  一个与业务无关的位置（本轮就发生了：canary 触发 off-by-one，整条流水线红两次）。改成「解析不出来的不算违规，
  但成功解析数必须 ≥8」之后，解析器失效与弹窗被删都会在同一条哨兵上响，且失败信息可读、不误伤别的提交。
- **为什么把「CI 红两次 + 真因」原样写进日志**：与 09-16「CI 红一次原样记进日志」同一条理由 —— 这不是手误，
  而是「本地无 JDK、只能靠 CI 当编译器」这个工作方式的必然产物。这轮还多一条可复用的排查法：
  **日志下载不到时，用 check-run annotations + job steps + 各 job 之间的差异（release 绿 / debug 红 ⇒ 问题在 `src/test`）
  把失败夹逼出来**，比盲改快得多。
