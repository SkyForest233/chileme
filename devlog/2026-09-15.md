### 1. 读流兜底：读异常不再杀进程（P0）

- **文件**：`data/FoodRepository.kt`
- **问题**：`dataStore.data` 在 IO 抖动 / 文件被占用时抛异常；19 个 `stateIn(SharingStarted.Eagerly)` 共享协程一旦收到异常，因 `viewModelScope` 未挂 `CoroutineExceptionHandler`，异常会交给线程默认处理器 → **进程被杀**；若表现为读阻塞（永不发射），首页 `ready` 门控又会让启动画面永久停留。
- **改动**：新增 `resilientRead(keyName, fallback, transform)`：`IOException` 先退避重试 2 次（300ms），仍失败则 `Log.e` + 回落 fallback。`rawFlow()` / `lightFlow()` 均改为建立在它之上（`lightFlow` 新增 `keyName`/`fallback` 两个参数，9 处调用点同步更新）；凭据两个 flow 合并为 `nutstoreCredentialKeysFlow()` 复用。
- **影响面**：读写语义不变（写仍受 `isCorrupt` 守卫保护），仅把「崩溃」降级为「本次读到默认值 + 日志」。

### 10. 本地快照 IO 下沉 + 过期清理口径

- **同源问题扫尾（顺手一起清）**：既然「件」的语义定成了 `quantity` 求和，就顺手把同一类文案全查了一遍，又发现两处同病：

- **规则落地**：带「件」= 按件求和；不带单位、且点进去是记录列表的筛选计数（首页三张统计卡）保留条数；归档/消耗/历史一律「条」。已写入 `docs/ARCHITECTURE.md` §5，避免下次再混。

### 13. 性能批（用户选定）：单次解码 + 设置页重组粒度 + 仓储写守卫集成测试

**13.1 同一份 JSON 不再重复解码（第三方 P1-3）**

### 14. CI 门禁：静态检查（ktlint + detekt）+ release/R8 验证

**14.1 加了什么**

`build.yml` 从一个 job 变三个（原 `build-debug` 原样保留）：

| job | 内容 | 意义 |
|---|---|---|
| `build-debug` | `assembleDebug testDebugUnitTest lintDebug` | 原样保留（合并成一次 Gradle 调用） |
| `static-gates` | `bash tools/ci-gates.sh`（ktlint + detekt） | 新：风格与静态分析门禁，PR 阶段就拦 |
| `release-r8` | `assembleRelease lintRelease -PallowUnsignedRelease=true` | 新：R8 代码裁剪 + 资源压缩 + release 专属 lint |

`release-r8` 是这批最值钱的一项：R8 / 资源压缩的问题**只在 release 构建出现**（运行时才用到的类被裁掉、资源名对不上…），而此前只有打 tag 时的 `release.yml` 才验证——等到发版那一刻才发现就太晚了。无签名凭据时用 `-PallowUnsignedRelease=true`（`app/build.gradle.kts` 明确支持该开关，不是静默回退签名策略）：产出用 debug 密钥签名的 release APK，可直接装机做 R8 冒烟测试；同时上传 `usage.txt/seeds.txt`，体积回归或「某个类被裁掉」时可据此定位。

**14.2 为什么是「脚本 + 独立二进制」而不是 Gradle 插件**

`tools/ci-gates.sh` 负责下载并用 sha256 校验 ktlint（GraalVM 原生二进制，不需要 JVM）与 detekt-cli（Maven Central，连带 `.sha256` 一起校验），然后跑 `app/src` 下全部 `.kt`。不走 Gradle 插件有三个理由：

1. ktlint / detekt 的 Gradle 插件对 AGP 9 / Gradle 9.7 / Kotlin 2.4 这种新组合支持滞后，插件在**配置阶段**报错会把整个构建（含 release 打包）拖垮；
2. 工具版本与校验和固定在脚本里，升级是一次显式、可 review 的改动；workflow 只缓存目录，不用改；
3. 脚本在没有 Android SDK 的机器上也能跑，本地与 CI 同一套规则。

报告同时写 `build/reports/gates/` 并打印到 stdout——artifact 常常拿不到，日志才是最后能看的地方（与 lint 的 `textOutput=stdout` 同一理由）。

**14.3 ktlint 只开 6 条规则（以及为什么）**

`ktlint_standard = disabled` + 显式开启：`no-wildcard-imports`、`final-newline`、`no-trailing-spaces`、`no-consecutive-blank-lines`、`no-blank-line-before-rbrace`、`string-template`。六条都已预检为零违规，开启即绿。

不全开的原因：standard 规则集对「1.7 万行、从未格式化过」的仓库会一次报出上千条纯格式差异，混进任何一轮功能改动都会让 review 失焦。全量格式化留待专门一轮（`ktlint --format` 刷一遍 + 单独 review 那份 diff），之后把 `ktlint_standard = disabled` 改成 `enabled` 即可升级门禁。

特别说明 `no-unused-imports`：ktlint 自 **1.7 起已弃用**该规则（官方 issue #3038 列了 20 多条误报案例，最严重的是把实际在用的 import 判成未使用、删掉后编译失败），1.8 需显式开启、2.0 将移除。本仓库改用 detekt 的 `UnusedImports`（同题下更保守的实现）兜底。

**14.4 detekt 的规则边界与灰度**

- 全开：`potential-bugs` / `coroutines` / `empty-blocks` / `performance` 四个「疑似缺陷」规则集；
- 部分开：`style` 只留 `UnusedImports` / `UnusedPrivateMember` / `UnusedPrivateProperty` 等高价值项，其余（`MagicNumber`、`MaxLineLength`、`ReturnCount`、`VarCouldBeVal`、`UseDataClass`、`ExplicitItLambdaParameter`…）逐条显式关闭并写明原因；
- 整体关闭：`complexity` / `comments` / `naming` / `exceptions`——对应用层业务代码偏严，属主观项。

灰度：detekt 1.23.8 内置的 Kotlin 编译器是 2.0.21（本工程 2.4.10），规则噪声需要按实际报告收敛，所以脚本里 `DETEKT_MODE` 默认 `report`（只报告不拦截）。首次 CI 报告出来后，确认解析正常、噪声可控 → 把 `DETEKT_MODE` 改成 `block`。这一步只改脚本一行，不需要再动 workflow。

## 💡 决策记录

- **为什么把读兜底放在仓库层而不是 VM**：19 个 flow 的收集点分散在 repository 与 VM 两处，逐个加 `catch` 必然漏；`rawFlow`/`lightFlow` 是所有读的唯一入口，收口一处即可全覆盖。
- **为什么不给 `viewModelScope` 挂 `CoroutineExceptionHandler` 就算完**：那只能阻止崩溃，flow 一旦失败该数据流就永久静默了（UI 停在旧值/空值且无提示）。仓库层兜底能保证「数据流继续活着」。
- **为什么 `previewBackup` 要求必须含 `items` 键**：`BackupData` 全字段带默认值，`{}` 能解码成功——不加这道判断，「格式错误友好提示」在**最危险的输入**（合法但空）上反而失效。
- **为什么快照失败仍允许导入**：导入的主要用途就是「当前数据已损坏时用备份覆盖」。因序列化失败而拒绝导入，会让用户彻底没有恢复手段。
- **为什么加静态守卫测试而不是自定义 lint**：源码就在仓库里，一个 JVM 单测读取 `Miuix*.kt` 断言即可，成本远低于写 lint 规则，且 CI 已经在跑单测。
