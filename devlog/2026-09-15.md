## ✅ 已完成

### 1. 读流兜底：读异常不再杀进程（P0）

- **文件**：`data/FoodRepository.kt`
- **问题**：`dataStore.data` 在 IO 抖动 / 文件被占用时抛异常；19 个 `stateIn(SharingStarted.Eagerly)` 共享协程一旦收到异常，因 `viewModelScope` 未挂 `CoroutineExceptionHandler`，异常会交给线程默认处理器 → **进程被杀**；若表现为读阻塞（永不发射），首页 `ready` 门控又会让启动画面永久停留。
- **改动**：新增 `resilientRead(keyName, fallback, transform)`：`IOException` 先退避重试 2 次（300ms），仍失败则 `Log.e` + 回落 fallback。`rawFlow()` / `lightFlow()` 均改为建立在它之上（`lightFlow` 新增 `keyName`/`fallback` 两个参数，9 处调用点同步更新）；凭据两个 flow 合并为 `nutstoreCredentialKeysFlow()` 复用。
- **影响面**：读写语义不变（写仍受 `isCorrupt` 守卫保护），仅把「崩溃」降级为「本次读到默认值 + 日志」。

### 2. 启动放行超时：不可能再卡在启动页（P0）

- **文件**：`MainActivity.kt`
- **改动**：`contentReady` 由普通 `var` 改为 `mutableStateOf`（超时翻转需触发重组），新增 `READY_TIMEOUT_MS = 3_000L`：`ready` 3 秒内未达成也强制渲染首帧。
- **取舍**：极端情况下会多显示一帧默认主题，但杜绝「永久停在启动画面、只能杀进程」。

### 3. 损坏态下不再删除封面图（P0，最严重的一处）

- **文件**：`viewmodel/AppViewModel.kt`
- **问题**：启动时的 `cleanupOrphanCovers()` 用 `itemsFlow.first()` / `archiveFlow.first()` 组装「被引用图片」集合；而解码失败时这两个流会按设计回落**空集**，于是 `covers/` 下所有文件被当成孤儿**全部删除**——而图片无法从 `corrupt/` 的 JSON 留档恢复。守卫本想救数据，清理逻辑却在同一时刻销毁数据。
- **改动**：`corruptedKeys` 非空时跳过清理并 `Log.w` 提示。

### 4. 过期浪费统计口径改为按件数

- **文件**：`ui/screens/StatsState.kt`
- **问题**：`wastedTotal = archived.count { reason == EXPIRED }` 数的是**归档条数**，而归档保留原 `quantity` —— 「6 瓶冰红茶过期」被统计成 1；同屏「本周消耗」却按件求和，一个屏幕两种口径。该指标是 App「减少浪费」价值主张的唯一量化出口。
- **改动**：抽成纯函数 `calculateWastedTotal(archived) = sumOf { it.item.quantity }`（可 JVM 单测），并在 KDoc 注明它仍受 `take(200)` 归档上限影响。

## 💡 决策记录

- **为什么把读兜底放在仓库层而不是 VM**：19 个 flow 的收集点分散在 repository 与 VM 两处，逐个加 `catch` 必然漏；`rawFlow`/`lightFlow` 是所有读的唯一入口，收口一处即可全覆盖。
- **为什么不给 `viewModelScope` 挂 `CoroutineExceptionHandler` 就算完**：那只能阻止崩溃，flow 一旦失败该数据流就永久静默了（UI 停在旧值/空值且无提示）。仓库层兜底能保证「数据流继续活着」。
- **为什么 `previewBackup` 要求必须含 `items` 键**：`BackupData` 全字段带默认值，`{}` 能解码成功——不加这道判断，「格式错误友好提示」在**最危险的输入**（合法但空）上反而失效。
- **为什么快照失败仍允许导入**：导入的主要用途就是「当前数据已损坏时用备份覆盖」。因序列化失败而拒绝导入，会让用户彻底没有恢复手段。
- **为什么加静态守卫测试而不是自定义 lint**：源码就在仓库里，一个 JVM 单测读取 `Miuix*.kt` 断言即可，成本远低于写 lint 规则，且 CI 已经在跑单测。
