## 第 26 轮：构建/兼容/数据安全四阶段修复（fix-plan 阶段 1–4）

> 起因：全仓库复审发现三个"本地跑不出来、只在发布或老设备上炸"的盲区。
> 方案见 `docs/audits/2026-08-21-fix-plan.md`（共 7 阶段，本轮做 1–4）。

### ✅ 阶段 1：发布链路（🔴 P0）

- **Release 签名此前完全失效**：`release.yml` 通过环境变量传 secrets，而
  `build.gradle.kts` 只读 `keystore.properties`，CI 中无人生成该文件 →
  `hasReleaseSigning` 恒为 false → 静默回退 debug 签名。
  已发布的 v1.0.0 / v2.0 / v2.0.1 **均由 CI 每次现生成的临时 debug key 签名**，
  签名互不相同，用户覆盖安装必然 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`。
  `Decode keystore` 步骤解出的文件从头到尾没被用过。
- 改为「环境变量优先 → keystore.properties 回退」；四项凭据缺一即
  `GradleException` 失败，不再静默降级；本地验证用 `-PallowUnsignedRelease=true`。
- `release.yml` 增加 apksigner 产物校验，检出 `CN=Android Debug` 直接 fail。
- `versionCode` 改由 `github.run_number` 注入（此前恒为 1，三个 tag 对系统是同一版本）。

### ✅ 阶段 2：运行时兼容（🔴 P0）

- **minSdk 24 → 26**。全项目 28 处 `java.time`（API 26 引入）且未开启 core
  library desugaring，API 24/25 设备一进首页就 `NoClassDefFoundError`
  （`daysLeft` 走 `ChronoUnit`）。按用户决策直接提 minSdk，不加脱糖。
- lint 中 `NewApi` / `InlinedApi` 提为 error，`build.yml` 增加 `lintDebug`
  步骤并上传报告 —— 此前 CI 只跑 `assembleDebug`，对这类问题完全沉默。

### ✅ 阶段 3：数据安全（🟠 P1）

- **解码失败此前会静默清空数据**：`Corrupt` 与 `Empty` 都回落 `emptyList()`，
  随后任一写操作（如 `upsert`）把空表 encode 覆盖 → 一次解析异常永久摧毁全部库存。
  引入三态 `Decoded(Ok/Empty/Corrupt)`，11 处写路径全部加 `isCorrupt` 守卫。
- 损坏原始串留档 `filesDir/corrupt/`，`corruptedKeys` 驱动首页告警条
  （`DataCorruptBanner`，MD3 / Miuix 共用）。
- `clearAll` / `clearArchive` / `importBackupJson` 作为恢复手段允许在损坏态执行；
  `buildBackupJson` 改为抛异常，防止残缺备份被导出或上传覆盖云端完好版本。
- 顺带修复 `compactConsumption` 聚合记录未生成 id —— 此前导致消耗记录页删除
  按钮**静默无效**，要等下次冷启动 `migrateConsumptionIds()` 才恢复。
- 新增 `backup_rules.xml` / `data_extraction_rules.xml` 排除 DataStore（Keystore
  密文不跨设备，恢复后必然解不开）；新增 `nutstoreCredentialBroken` 状态，
  设置页提示「应用密码已失效，请重新填写」。
- `file_paths.xml` 由 `path="."` 收窄为仅 `camera/` + `covers/`。

### ✅ 阶段 4：性能（🟠 P2）

- 7 个列表 flow 改走 `rawFlow`：取原始串 → `distinctUntilChanged` → 解码 →
  `flowOn(Default)`。此前 DataStore 每次重发整份 Preferences 都会让全部 key
  重新解析 JSON 并产生新 List 实例（**改一次主题色即触发全屏重组**），
  且解码跑在 `viewModelScope`（`Main.immediate`）主线程。
- 密码流按密文去重后再解密，避免每次重发都在主线程做一次 Keystore AES-GCM。

### ⚠️ 已知影响 / 待办

- **已发布的三个 Release 无法追溯修复**。签名变更后老用户无法覆盖安装，
  下个 Release notes 必须注明「请先在设置页导出备份，卸载旧版后再安装」。
- 阶段 5（单测基线）、6（无障碍/README）、7（MD3+Miuix 双实现去重）待讨论。

### 💡 决策

- 签名失败要"响亮"：静默回退正是问题能藏三个版本的根因，故改为直接 fail。
- 损坏守卫只覆盖四个「用户资产型」key；配置型 key 丢了能重设，维持回落默认值，
  避免为了完备性把 26 处 `edit` 全部改重。
- 阶段 3 与 4 都在 `FoodRepository` 的同一批 flow 上动刀，合并为一个 commit 更省事。
