## §3 沙箱会被重建：`git apply` 打在错误基线上 + `git checkout -- .` 从 index 恢复

今天最险的一下：`git apply` 那份补丁后跑 `git diff --stat`，冒出 **37 个文件、+1453/−1073**，里面全是
`CloudSync.kt`(-170) `StatsScreen.kt`(-291) `AppChrome.kt`(-259) 这种"我几轮前改过的文件被退回去了"的形状 ⚠️⚠️。
真因不在补丁（`grep -c "^diff --git"` 实测它只含 2 个文件的 diff），在**这个沙箱被平台重建过**：reflog 只有 `clone → checkout → reset` 三条，
⇒ 本地 `.git` 是本轮新 clone 的、分支指针停在会话基线 `f302138`，而**工作区的文件是我 latest 的内容**（文件层由平台
按 turn 快照恢复，与 `.git` 不同步）⇒ `git status` 那 65 行"已修改"其实是"我的工作 vs 基线"，`git diff` 也是。
⇒ 连环两次自我伤害：`git checkout -- .`（**从 index 恢复、不是从 HEAD**）把工作区刷成基线内容；
`git reset --hard HEAD`（此时 HEAD=基线）再确认一遍。救回靠的是**远端**：`git fetch origin <branch>` +
`git reset --hard origin/<branch>` ⇒ 回到 `0af6da4`，`git status` 干净、`doc-metrics` 与 `@Test` 计数（206）全部对上。
零丢失，唯一原因是**每笔都推了远端**。

**新自查口径（已写进 `docs/WORKFLOW.md` §4）**：动手改文件之前先跑一次
`git log --oneline -1` 与 `git ls-remote origin <本分支>` 对齐 —— 不一致就说明沙箱被重建过，此时**禁止**
`git checkout -- .` / `git reset --hard`（它们会把工作区刷成基线），正确动作是先 fetch 再 `reset --hard origin/<branch>`。
⚠️ 附带一条：对历史遗留的 `*.patch` 用 `git apply` 之前，除了 `--check`，还要看**应用后 `git status` 的改动面**是否等于
补丁的文件数 —— 不等就说明基线不对，`git apply` 不会报错，只会静默改一堆别的文件。

§3 那条口径（动手前先比对 `git log -1` 与 `git ls-remote`）落地不到一小时，本段就是它的续集：本轮**中途**又重建了一次，
这次更阴 —— 我给文档写小改动的脚本先因语法错误**没改成任何文件**，但 `&&` 链后面的 `git add -A && git commit` 照跑 ⇒
在"本地 HEAD 已退回基线 `f302138`、工作区却是最新内容"的状态下，把**整个工作区（66 个文件 / +5423 行，连两份
`tools-tmp-*.py` 草稿都算上）压成一笔 `eddf38a` 挂在基线上** ⚠️⚠️。是 `git push` 替我拦住的：
`non-fast-forward`（远端早已是 `8fd7bcd`）⇒ 那笔垃圾提交没进远端历史。
恢复：`git fetch origin <branch>` + `git checkout -B <branch> FETCH_HEAD` ⇒ 工作区与 `8fd7bcd` 逐字节一致（`git status` 干净）。

**两条习惯改进（已写进 `docs/WORKFLOW.md` §4 新行「沙箱在轮次中途重建」）**：
1. 比对基线**不能只在轮次开头做一次** ⇒ **每次 `git commit` 之前**都看一次 `git log --oneline -1` 是否还是本轮开头的尖端。
2. **不要把 `git add -A && git commit` 接在可能失败的脚本后面**当"顺手一批"：脚本失败时 `add -A` 吞进去的是整片工作区，
   不是你打算提交的那几份。顺带清掉的历史垃圾：`tools-tmp-11a.py`(128) 与 `tools-tmp-docs.py`(58) 是 #11a 那笔（`9a9d967`）
   用 `add -A` 时混进来的就地改文件脚本 ⇒ 本笔 `git rm` 掉并把 `tools-tmp-*` 加进 `.gitignore`（同一形状的漏洞还会再犯，
   堵住比记仇有效）。

顺带结一项决定：**#9 那 4 个 workflow 小项 + 那份 action 升级补丁，用户 09-20 决定整体先不动**，等上架窗口打开再一并处理 ⇒
