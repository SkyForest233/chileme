### 2. #4a：一次性 UI 事件从「可空 StateFlow + 手工 consume」→ `UiEvent` + `Channel`

**改之前是什么样**：4 处「看过一次就该消失」的提示，全都建成 `MutableStateFlow<X?>(null)` + 一个 `consumeXxx()` 手工清空 ——
`_undoRequest`（列表页减号 → 撤销消耗）、`_deletedConsumption`（消耗记录页删除 → 撤销）、
`_restoredArchivedEvent`（搜索里恢复归档 → 撤销）、`_autoSyncMessage`（启动自动同步成功提示）。

`StateFlow` 会向**新订阅者重放最后一个值**，所以「看过就撕」全靠每个收集点记得调 `consume`。
今天 4/4 都记得 ⇒ **并没有正在发生的重放 bug**。但那是纪律不是机制：新加第 5 个事件、或某个收集点漏调一次，
症状是「旋屏后同一条提示又弹一遍」，非常难查。改成 `Channel` 后**接收即出队**，`consume` 函数与可空状态一起消失。

**实施时推翻了计划里的两处设想**（都记进 ROADMAP #4「4a 落地结果」，不是照原计划硬做）：

1. **落点是三个不是两个**。规划时只读了 `MainApp` 与消耗记录页，**漏了首页 `AppScaffold` 自己的宿主** ——
   自动同步提示一直落在那里。这是"读得不够就下手"的典型，动手写代码时才撞见。
2. **「一个 `Channel` + 一份收集实现挂多处」不成立**。`Channel` 是**单接收方**语义：多个收集协程会互相抢事件
   （谁先 `receive` 谁拿到，结果不确定）。所以按落点分了**三条队列** —— 发送端仍只有一处（`emit()`），
   每条队列恰好一个接收方，接收方生命周期与该宿主一致。

   也考虑过「干脆统一到主壳一处收集」，被否掉的理由比落位更硬：`showSnackbar` 会**挂起到提示关闭为止**，
   若用户已经离开首页，就往那个**没有渲染**的宿主发提示 ⇒ 收集协程被永久堵住，之后所有撤销条都不再出现。
   队列化正好复现旧行为：事件在队列里等着，用户回到那一页才弹。

**为什么是 `Channel(BUFFERED)` 而不是 `SharedFlow(replay=0)`**：`MainActivity` 的主题分支会让 `MainApp` 整棵重组
（切主题 = 旧组合销毁、新组合建立），`replay=0` 的 SharedFlow 会在这个瞬间**把事件直接丢掉**；
`Channel` 是排队，切换完成后照弹。

**唯一的逻辑删除**：`undoDeleteConsumption` 里那句「若待处理的撤销事件正是这条记录就清空它」。
收集端一直是「先 consume 再弹条」，弹条期间那个状态早已是 `null`，故那句**永远不成立**；
改用 `Channel` 后也没有「待处理的事件」可清 ⇒ 删掉，理由写在代码注释里。
除此之外 4 条提示的**文案、落位、主题分流逻辑逐句未改**（这是"纯搬运"的判据）。

### 8. #4b：主壳三处「按主题分流」收成一个 helper + 把文案与落位钉进 CI（提交 `265193f`）

**范围被 4a 的实施结果改过**（ROADMAP 的 4b 行已整行重写）：原计划「新增一份 `UiEventHandler` 挂在每个
Snackbar 宿主上」做不到 —— 三个落点的宿主类型不同（主壳是两个裸 host、二级页是 `AppSnackbarHostState`），
且收集协程必须与宿主同生命周期。所以 4b 只做真正重复的那部分：**分流**。

- `ui/components/UndoSnackbar.kt` 新增 `internal suspend fun showUndoSnackbarAcrossThemes(isMiuix, md3Host,
  miuixHost, message): Boolean`，放在两个 `showUndoSnackbar` 扩展旁边；
- `MainApp` 三处形状完全相同的 if/else 各收成一次调用（撤销消耗、恢复归档、**批量归档** —— 第三条不走事件系统，
  是 `archiveSelected()` 里 `scope.launch` 的直接调用；重复的是"分流"，与走不走事件无关）；
- 删掉随之失效的 3 条 import（`SnackbarResult`、`MiuixSnackbarResult` 别名、`showUndoSnackbar`）⇒
  主壳里 `SnackbarResult` 字样实测 **0** 处；净 −4 行（+21/−25）。

**一个被否掉的更"干净"方案**：让主壳直接用二级页那个 `AppSnackbarHostState`（它已经把分流收在容器里了）。
否掉的理由是生命周期而不是审美：那容器是 `remember(isMiuix)` 建的，切主题会换**新**容器与新宿主，
而主壳的收集协程是 `LaunchedEffect(Unit)`（key 一变就取消协程、中断 `showSnackbar` —— 当年 MD3 撤销条不出现的
根因），协程捕获的还是旧容器 ⇒ 提示弹到**没有渲染**的宿主上，而 `showSnackbar` 挂起到关闭为止

## 💡 决策记录

1. **`Channel(BUFFERED)` 而非 `SharedFlow(replay=0)`**：切主题会销毁并重建 `MainApp` 整棵组合，
   `replay=0` 会在这个瞬间丢事件；`Channel` 排队，切换完照弹。
2. **三条队列而非一条**：`Channel` 是单接收方语义，多收集协程会互相抢（详见 §2）。
3. **发送端一处、接收端三处**：`emit()` 按 `UiEvent.surface` 分流是唯一的发送点（可断言）；
   接收端必须与宿主同生命周期，所以是三处。
4. **事件载荷是数据不是回调**：回调会捕获发出时那个界面的宿主对象，跨主题/跨页面即失效；
   而且"跨主题宿主对象不得漏回屏幕层"是本仓既有架构约束（`docs/ARCHITECTURE.md:157`）。
5. **不启用 detekt `UnusedImports`**：门禁调整要单独一轮，本地检查器已覆盖。
6. **守卫随重构交接，不留两套**：临时守卫在同一次提交里换成正式守卫（§6a）。
7. **历史数字不加粗、现值加粗**：让"会被断言的数"与"只是历史记录的数"在排版上就能区分（§6b）。
8. **4b 用自由函数而不是让主壳复用 `AppSnackbarHostState`**（§8）：容器带 `remember(isMiuix)`，
   切主题换宿主，会把主壳那条 `LaunchedEffect(Unit)` 协程堵死在没渲染的宿主上。**宿主身份稳定性 > 抽象统一性**。
9. **helper 用 `internal` 而不是 `public`**：只有主壳需要它，`internal` = 只给本模块，不进公开 API 面；
   二级页继续走 `AppSnackbarHostState`，两条路各有各的道理，不强行合并。
10. **失败分三档而不是四档**（§9）：不给 HTTP 状态码单列一档 —— 状态码本来就在文案里、用户看得见，
    而 UI 目前对 507 与 500 没有任何不同处理。为一档没人区分的情况加类型，只是让 `when` 多一个分支。
11. **`CloudBackupsEmpty` 必须单独一档**：改造前 `onResult(false, "云端暂无备份…")` 把"成功但没东西"
    塞进了失败那一档；天真地换成 `Result` 会让界面把"云端是空的"当错误处理。**语义被压平的地方要拆开，
    不能只换载体**。
12. **`syncUpload` 的本地打包失败显式用 `OpFailure.Other`，不走 `toOpFailure()`**：结果虽同，
    但显式写才表达得出"这是本地数据问题、不是网络问题"；把本地错误分类成网络错会误导用户去重试。
13. **改名趁早**（§10 #2）：`SyncFailure`/`SyncOp` → `OpFailure`/`DataOp` 在动手当天就改了 ——
    "导入备份"与"快照损坏"都不是同步操作，装不进那个名字；等到引用铺开再改，成本与风险都大得多。
