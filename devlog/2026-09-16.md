## ⚠️ 本轮新发现（此前**任何**文档都没登记）

① **`ARCHITECTURE.md` 教人硬编码 FileProvider authority**（已修，见上 §2）。这不是笔误级问题：`namespace = com.agon.app` 与 `applicationId = com.chileme.pantry` 是刻意分离的，按原文写死 `com.agon.app.fileprovider` 会在拍照时抛 `IllegalArgumentException`，而 `CLAUDE.md` §5 的约束恰好是反的 —— 两份文档给出相反指令。

② **换机直传会产生一批孤儿封面**：`data_extraction_rules.xml` 的 `device-transfer` 放行 `covers/` 却排除 `datastore/` → 封面图传到新机、引用它的库存 JSON 没传，新机首次启动 `cleanupOrphanCovers()` 会把这些图当孤儿删掉。不致命（数据本来就没过去），但白传一轮图片。已登记进 `ARCHITECTURE.md`，**未改行为**（要不要让 `device-transfer` 也排除 `covers/`，或反过来让库存数据也能换机直传，属产品决策）。

③ **`filesDir/snapshots/` 未被任何备份规则排除** → 每日全量库存 JSON（最近 3 份）会随 Android 系统备份进入用户自己的 Google 账号。这是 `chileme-review.md` P0-6 里**唯一站得住**的部分（该条主体论点是误判）。已在 `ARCHITECTURE.md` 登记 + README 隐私段落如实说明；**未改规则**，因为「让库存数据随系统备份走」其实可能是用户想要的（与 ② 是同一个决策的两面）。

④ **`REQUIREMENTS.md` §4 与 F20 自相矛盾**（已修，见上 §5）。「❌ 云同步」与「F20 坚果云同步」同时存在于同一份「唯一事实源」里，任何按 §4 判断需求边界的人都会得出错误结论。

## 💡 决策记录

- **为什么历史审查报告只加批注、不改写原文**：这三份报告是「当时的判断」的记录，价值在于可追溯（包括判断错的那条）。直接改写会让后来人无法理解后续修复的动因，也会掩盖 P0-6 这类误判——而误判本身是有信息量的（它说明「读文件时凭印象下结论」的风险）。所以一律文首/标题加状态批注，原文保留。
- **为什么把 F22–F43 补进 `REQUIREMENTS.md` 而不是另开一份「已实现功能清单」**：该文件自我定位为「功能范围的唯一事实源」，且规定「新需求必须先在此登记再开发」。已经上线的 22 项功能不在里面，等于这份事实源缺了三分之二，任何人（含 AI）拿它判断需求边界都会错。补登记比另开文件更能恢复它的作用。
- **为什么只改 KDoc 而不补 MIUIX 配色入口**：补入口需要 `MiuixRootTheme` 打通种子色通道（Miuix `ThemeController` 的 `keyColor`），属功能开发且用户已明确暂缓；而错误的「功能对等」声明是**当下就在误导人**的，改注释零风险。
- **为什么 ②③ 只登记不改行为**：两者是同一个产品决策的两面（要不要让数据随系统通道迁移），任一侧单独改都可能与用户意图相反。按 `CLAUDE.md` §4.2「超出范围的需求先与用户沟通确认」处理。
- **为什么本轮不跑构建就交付**：改动是 12 份 Markdown + 1 处 KDoc 注释，无编译语义变化；沙箱既无 JDK/SDK，ktlint 二进制又被网络策略拦截（`curl: (35) SSL_ERROR_SYSCALL`）。按 `CLAUDE.md` §4.4 以 CI 为验收，本轮 CI 需确认三点：`assembleDebug` 仍绿、ktlint 仍零违规（KDoc 改动是唯一被检文件）、116 例单测不受影响（未动任何测试与被测代码）。
