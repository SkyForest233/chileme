### #7 字符串资源化 + 无障碍补全（可随时插队）

- **前置：无**。原路线图要求「#3 去重后再做，否则同样的文案要改两遍」——双主题合并已完成，这个前置已经满足，
  也不必等 #4 / #5。
- **规模（不要手抄）**：跑 `bash tools/doc-metrics.sh` 看两行——
  「`strings.xml` 条目」与「含中文的字符串字面量」（两者之差就是待资源化的规模）；
  「`contentDescription = null`」与「`Modifier.semantics` 真调用」两行就是无障碍缺口。
  ⚠️ 历史证据行写过「583 / 虚高 591」，两天就腐烂（核查第 19 处，原文见快照）；另有一份历史报告写「7 处 semantics」，
  那是**把 6 行 import 也算进去了**的口径，别复用。
- **做法与顺序**：先补无障碍（改动小、收益直接、可用守卫拦），再做资源化（机械但量大，**按屏幕分批**）。
- **外部评审补的缺口**（`docs/audits/2026-09-19-independent-review.md` §6.3）：到期日历的日期格**只用纯颜色圆点**表达
  紧急度，单元格本身没有任何语义 ⇒ TalkBack 用户只读得到数字、色觉障碍用户同样丢信息（官方 a11y 硬指标是
  「不得仅用颜色传达信息」），加一条 `semantics { contentDescription = … }` 成本很低；`QuantityStepper` 这类加减控件
  建议用 `Modifier.toggleable` / 显式 `Role` + `stateDescription`。
- **验收**：`contentDescription = null` 逐条判定为「刻意留空（装饰性）」或「补上描述」，**不允许有未判定的**；
  图表与日历补语义后能被 TalkBack 读出数据；资源化按屏幕给验收（例如「设置页全部入 `strings.xml`」）。
- **同批要处理的守卫**：屏幕新增 `stringResource` 时 `ScreenParityTest` 的「逐字相同」类断言不受影响，
  但 `ImeHandlingTest` / `CorruptGuardTest` 那类**按文件路径点名**的守卫要确认路径没变
  —— 搬走一个文件 = 让某条断言读到空串（假绿）或直接红。

### #6 派生数据下沉 + `WhileSubscribed` —— ⏸ 搁置（2026-09-19 用户决定 `skip_10c`）

- **本项剩下的只有一件事**：给 `AppViewModel` 里的 `stateIn(` 加 `WhileSubscribed(5_000)`。
  另一半「派生数据下沉」已不成立——屏幕层的业务聚合被 `ScreenParityTest` 拦着，宽口径只剩几处且都不是业务聚合
  （3 处是输入框只留数字、1 处是历史记录筛选、1 处是图表绘制适配），证据见快照 #6 节。
- **为什么不能上来就改那个词**：`Eagerly` 顺手承担了一个**安全职责**——从 VM 创建起就在收集，所以任何时候读 `.value`
  都是真数据；全仓有多处正是这样「直接读缓存值」。其中编辑页那处（`EditFoodScreen.kt` 里
  `remember(editId) { viewModel.items.value.find { … } }`）**会丢数据**：该屏**不收集** `items`，进程被系统杀掉后
  恢复到编辑页时读到的是冷值 ⇒ 表单按「新增」初始化成空白，用户点保存就把这个食品清空。
  今天不出事，靠的是 `Eagerly` 与 `ready` 首帧门控配合（启动屏挡住首帧，门控放开时数据已到）。
  VM 侧那些读点都在 `viewModelScope.launch { }` 里 ⇒ 可改 `repo.<x>Flow.first()`。
- **重启条件与顺序（照此走，别跳步）**：① **加固提交**（前置）：VM 侧的 `.value` 读改 `.first()`
  （`Eagerly` 下与 `.value` 同值 ⇒ 行为等价）+ 编辑页那处**真行为改动**（先订阅、数据没到就不渲染表单），单独标注；
  ② 再按三档关预热——主题与门控 → 设置页 → 数据列表，**一档一提交、逐档可回滚**；
  ③ 最后一轮两主题真机复测（重点四条：进程被杀后恢复到编辑页 / 分类管理页增删改 / 坚果云上传下载 / 撤销链路）。
- **⚠️ 落地那一刻会连带报红**：`doc-metrics` 里写死 `WhileSubscribed` 的行会有 4 处报不符，其中 1 处在
  `docs/audits/2026-08-21-compose-audit.md` 里（审计报告按约定**只加批注、不改写原文**）
  ⇒ 必须与第一档同批处理，做法是把 `docs/audits/` 排除出该项比对（工具改动、单独提交）。
  清单与顺序见快照「#6」节与 `devlog/2026-09-19.md` §11。

## 决定记录：DataStore → Room **不迁**（2026-09-20）

- **判定**：现在不迁。不是「Room 不好」，而是「现在迁它的净收益 < 净代价」，且代价在本项目的处境下被放大
  （三件事只能真机验、备份 JSON 契约必须原样保留、按源码形状写的守卫必红）。
- **一条关键理由**：评审把「归档静默截断」定级 P0，那是**迁 Room 的最大理由**，而 M1-3 已就地把这条修掉
  （`ARCHIVE_RETENTION` + `archive_overflow_total`）。官方那句「大数据集 / 部分更新 / 引用完整性才用 Room」
  的三个条件目前一个都不成立（筛选/排序/聚合都在 Kotlin 侧，单机单用户、`edit` 天然串行、无 JOIN 需求）。
- 逐项实测表（写放大是否真存在、迁移要付的账、只能真机验的三件事、数据形状是否需要 SQL）见快照「决定记录」节。
- **触发线（任一成立就重新评估，写成可测的）**：
  ① 单次「改数量」写路径的序列化条目数 **> 3,000**（`items` + `consumption` + `archive` 三表之和）；
  ② 出现**任何**需要跨表查询 / 分页 / 全文搜索的功能（Kotlin 侧 `filter` 会先变成卡顿）；
  ③ `MAX_BACKUP_BYTES`（定义在 `data/BackupFile.kt`，20 MB）被真实用户顶到 ⇒ 备份/恢复被拒 = 数据安全事故级。
- **押后项的新指针**：`FoodRepository.kt` 的 key / flow 归位 ⇒ 挂到「分片或 Room 的那一次」；
  **#6 / 10c 与存储无关**（卡的是 `Eagerly` 的安全职责），不要因为它们都在这里被提到就捆在一起做。
