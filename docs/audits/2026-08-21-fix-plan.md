## 阶段 1 · 发布链路修复（🔴 P0-1 + P4）

### 问题复述

1. `.github/workflows/release.yml:38-44` 通过 **环境变量** 传签名信息，但 `app/build.gradle.kts:11-15` **只读 `keystore.properties` 文件**，CI 中无人生成该文件 → `hasReleaseSigning == false` → `app/build.gradle.kts:74` 静默回退 debug 签名。
   - `Decode keystore` 步骤解出的 `keystore/release.keystore` 从未被使用。
   - 后果：GitHub Releases 上 v1.0.0 / v2.0 / v2.0.1 均为**每次 CI 现生成的临时 debug key** 签名，签名互不相同 → 用户覆盖安装报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`，只能卸载重装（数据全丢）。
2. `app/build.gradle.kts:32` `versionCode = 1` 恒定，三个 tag 对系统而言是同一版本。

### 修复设计

**1.1 让 Gradle 优先读环境变量，保留 `keystore.properties` 作为本地回退**

`app/build.gradle.kts`：

```kotlin
// 签名凭据优先级：环境变量（CI / GitHub Secrets）> keystore.properties（本地，不入库）
val keystoreProperties = Properties().apply {
    val f = rootProject.file("keystore.properties")
    if (f.exists()) f.inputStream().use { load(it) }
}

fun signingValue(env: String, prop: String): String? =
    System.getenv(env)?.takeIf { it.isNotBlank() }
        ?: keystoreProperties.getProperty(prop)?.takeIf { it.isNotBlank() }

val releaseStoreFile     = signingValue("RELEASE_KEYSTORE_PATH", "storeFile")
val releaseStorePassword = signingValue("RELEASE_KEYSTORE_PASSWORD", "storePassword")
val releaseKeyAlias      = signingValue("RELEASE_KEY_ALIAS", "keyAlias")
val releaseKeyPassword   = signingValue("RELEASE_KEY_PASSWORD", "keyPassword")

val hasReleaseSigning = releaseStoreFile != null && releaseStorePassword != null &&
    releaseKeyAlias != null && releaseKeyPassword != null
```

`signingConfigs.create("release")` 内改用上述四个变量。

**1.2 禁止 release 静默降级为 debug 签名**

不再无条件回退。改为：**未显式声明"允许未签名构建"时，release 必须有正式签名，否则 configuration 阶段 fail。**

```kotlin
// 本地无密钥时可用 -PallowUnsignedRelease=true 跑通 assembleRelease 做体积/R8 验证；
// CI 不传该参数，因此凭据缺失会直接失败，杜绝"发出去才发现是 debug 签名"。
val allowUnsignedRelease = providers.gradleProperty("allowUnsignedRelease")
    .orNull?.toBoolean() ?: false

release {
    signingConfig = when {
        hasReleaseSigning -> signingConfigs.getByName("release")
        allowUnsignedRelease -> signingConfigs.getByName("debug")
        else -> throw GradleException(
            "Release 签名凭据缺失。CI 请检查 RELEASE_KEYSTORE_* secrets；" +
            "本地验证请加 -PallowUnsignedRelease=true。"
        )
    }
}
```

**1.3 versionCode 由 CI 注入**

```kotlin
// tag 构建用 GITHUB_RUN_NUMBER 单调递增；本地开发回落 1。
versionCode = (System.getenv("APP_VERSION_CODE")?.toIntOrNull()) ?: 1
versionName = System.getenv("APP_VERSION_NAME") ?: "1.0"
```

`release.yml` 的 build 步骤补：

```yaml
env:
  APP_VERSION_CODE: ${{ github.run_number }}
  APP_VERSION_NAME: ${{ github.ref_name }}   # 仅 tag 构建；分支构建留空回落 1.0
```

> ⚠️ 与 `CLAUDE.md` §5「版本号锁定 v1.0」的关系：该约束锁的是**设置页展示的 versionName**。设置页目前是**硬编码字符串 "v1.0"**（`SettingsScreen.kt` / `MiuixSettingsScreen.kt`），不读 `BuildConfig`，因此本改动**不影响设置页展示**，与用户 2026-07-31 的要求不冲突。需在 `CLAUDE.md` 补一句说明，避免后续 AI 误改。

**1.4 `release.yml` 补 `keystore.properties` 兜底（可选，二选一即可）**

若倾向"不改 Gradle 逻辑"，则改为在 CI 生成文件：

```yaml
- name: Write keystore.properties
  run: |
    cat > keystore.properties <<EOF
    storeFile=keystore/release.keystore
    storePassword=${{ secrets.KEYSTORE_PASSWORD }}
    keyAlias=${{ secrets.KEY_ALIAS }}
    keyPassword=${{ secrets.KEY_PASSWORD }}
    EOF
```

**推荐 1.1 + 1.2（env 优先）**：凭据不落地成文件，且本地/CI 同一套逻辑。

### 验收

- 打一个测试 tag（如 `v2.0.2-rc1`）→ Actions `Build Release APK` 绿灯；
- 下载产物执行 `apksigner verify --print-certs app-release.apk`，确认签名指纹 = 正式 keystore，而非 `CN=Android Debug`；
- `aapt dump badging` 确认 `versionCode` 不再是 1。

### 风险 / 回滚

- 风险：secrets 名称与现有配置不符会导致 configuration 直接 fail（这是**期望行为**，比静默降级好）。
- 回滚：revert 单个 commit 即可，不涉及源码。
- ⚠️ **历史包袱**：已发布的三个 Release 无法追溯修复。建议在下一个 Release notes 里注明"**本版本起签名变更，需卸载旧版后安装；请先在设置页导出备份**"。

## 阶段 2 · 运行时兼容修复（🔴 P0-2）

### 问题复述

`minSdk = 24`，但全仓库 **28 处 `java.time`**（`LocalDate` 15 / `DateTimeFormatter` 2 / `ChronoUnit` / `Instant` / `YearMonth` / `ZoneOffset` / `LocalDateTime`），而 `java.time` 是 **API 26** 引入。`compileOptions` 中**既无 `isCoreLibraryDesugaringEnabled`，也无 `coreLibraryDesugaring` 依赖**。

`FoodModels.kt:130` 的 `daysLeft` → `ChronoUnit.DAYS.between(LocalDate.now(), ...)` 是首页首屏必经路径 → **API 24/25 设备开屏即 `NoClassDefFoundError`**。

`assembleDebug` 不报错，CI 也未跑 `lint`，所以此洞可一路带到用户手中。

### 修复设计（二选一）

**方案 A（推荐）：`minSdk = 26`**

```kotlin
minSdk = 26
```

- 理由：2026 年 API 24/25（Android 7.x）存量占比已可忽略；避免脱糖带来的 ~200KB 包体与额外 L8 构建耗时；`Build.VERSION` 判断可简化。
- 副作用：需同步 `docs/ARCHITECTURE.md` §1 的 minSdk 记录。

**方案 B：开启 core library desugaring（保住 24）**

```kotlin
compileOptions {
    isCoreLibraryDesugaringEnabled = true
    sourceCompatibility = JavaVersion.VERSION_21
    targetCompatibility = JavaVersion.VERSION_21
}

dependencies {
    coreLibraryDesugaring("com.android.tools:desugar_jdk_libs:2.1.5")
}
```

- 注意 AGP 9 的 L8 使用了新的精简合成类名格式，与 `-dontobfuscate` 的 R8 配置无冲突，但需实测 release 构建体积变化。

### 2.2 CI 补 lint（无论选 A 还是 B 都要做）

`.github/workflows/build.yml` 增加：

```yaml
- name: Lint
  run: ./gradlew lintDebug --no-daemon

- name: Upload lint report
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: lint-report
    path: app/build/reports/lint-results-debug.html
```

并在 `app/build.gradle.kts` 中把 `NewApi` 提为致命：

```kotlin
lint {
    warningsAsErrors = false
    abortOnError = true
    error += listOf("NewApi", "InlinedApi")
}
```

> 这是本次唯一能**从机制上防止同类问题复发**的改动，优先级等同于修复本身。

### 验收

- Actions `Build` 绿灯且 lint 报告中 `NewApi` 为 0；
- 选方案 B 时，额外确认 release APK 体积增量可接受（当前 ≈2.6MB）。

## 阶段 3 · 数据安全（🟠 P1 及相关）

### 3.1 解码失败不得静默清空（核心）

**现状**（`FoodRepository.kt:44-56`）：

```kotlin
raw?.let { runCatching { json.decodeFromString<List<FoodItem>>(it) }.getOrDefault(emptyList()) } ?: emptyList()
```

解析失败与"无数据"被压成同一结果；随后任意写操作（如 `upsert` :169）会 `decode → 空表 → encode 覆盖`，**一次解析异常即永久摧毁整份库存**。archive / consumption / history 四处同构。

**设计**：区分「无数据」与「解析失败」，失败时**中止写入**并对用户可见。

```kotlin
/** 解码结果：Empty=无数据；Ok=成功；Corrupt=存在原始串但解析失败（禁止覆盖写）。 */
private sealed interface Decoded<out T> {
    data class Ok<T>(val value: T) : Decoded<T>
    data object Empty : Decoded<Nothing>
    data class Corrupt(val raw: String, val cause: Throwable) : Decoded<Nothing>
}

private inline fun <reified T> decode(raw: String?): Decoded<T> = when {
    raw == null -> Decoded.Empty
    else -> runCatching { json.decodeFromString<T>(raw) }
        .fold({ Decoded.Ok(it) }, { Decoded.Corrupt(raw, it) })
}
```

改造要点：

1. **读路径（Flow）**：`Corrupt` 时发出空列表以保证 UI 不崩，同时置位 `corruptedKeys` 状态。
2. **写路径（26 处 `dataStore.edit`）**：读到 `Corrupt` 立即 `return@edit`，**不执行任何 `encodeToString` 覆盖**。
3. **取证**：首次检测到 `Corrupt` 时，把原始串另存到 `filesDir/corrupt/<key>-<timestamp>.json`，供用户导出求助与后续人工恢复。
4. **UI 提示**：`AppViewModel` 暴露 `dataCorrupted: StateFlow<Boolean>`，首页顶部显示一条警示条（"部分数据读取失败，已暂停写入以防丢失，请前往设置导出诊断文件"）。

> 收敛改动量的折中做法：仅对 **items / archived / consumption / history** 四个"用户资产型"key 走完整方案；thresholds / categories / locations 这类配置型 key 维持现有 fallback 到默认值的行为即可（丢了可重设，且 `decodeCategories` 已回落 `DefaultCategories`）。

### 3.2 `compactConsumption` 聚合丢失 `id`

`FoodRepository.kt:440` 构造聚合记录时未传 `id` → 聚合后的记录 `id == null` → `ConsumptionLogScreen.kt:144` 的 `record.id?.let { ... }` 静默失效，**删除按钮点了没反应**，直到下次冷启动 `migrateConsumptionIds()` 补 id 才恢复。

修复：聚合时生成新 id。

```kotlin
ConsumptionRecord(
    ...,
    id = UUID.randomUUID().toString(),
)
```

### 3.3 云备份排除敏感凭据

`AndroidManifest.xml:11` `allowBackup="true"` 且无 `dataExtractionRules` → 整个 DataStore（含 Keystore 密文 `nutstore_password_enc`）进入云备份。密文在新设备上**必然解不开**（Keystore 密钥不跨设备），而 `nutstorePasswordFlow` 解密失败直接 `?: ""`，用户会得到一个"看起来已配置、但同步永远失败"的账号且无任何提示。

修复：
- 新增 `res/xml/backup_rules.xml` + `res/xml/data_extraction_rules.xml`，排除 DataStore 文件（或至少在恢复后清空凭据 key）；
- Manifest 挂 `android:dataExtractionRules` / `android:fullBackupContent`；
- `SecureStore.decrypt` 返回 null 时，UI 提示"云同步凭据已失效，请重新填写应用密码"。

### 3.4 收窄 FileProvider 授权范围

`res/xml/file_paths.xml` 当前是 `<cache-path path="."/>` + `<files-path path="."/>`，把**整个私有目录**纳入可授权范围。实际只需两处：

```xml
<paths>
    <cache-path name="camera" path="camera/" />
    <files-path name="covers" path="covers/" />
</paths>
```

（对应 `EditFoodScreen.kt:171` 的 `cacheDir/camera/` 与 `ImageStore.kt:17` 的 `filesDir/covers/`。）

### 验收

- 手工构造损坏数据（adb 改写 DataStore 或导入畸形 JSON）→ 确认 App 不崩、显示警示条、**重启后原数据仍在**；
- 聚合后的消耗记录可正常删除；
- `adb shell bmgr` 走一遍备份/恢复，确认凭据未被跨设备带过去。

## 阶段 4 · 性能（🟠 P2）

### 问题复述

7 个 `xxxFlow` 均为 `dataStore.data.map { decode(...) }`，在 VM 中 `stateIn(viewModelScope, Eagerly, ...)`；`viewModelScope` 为 `Main.immediate`，**JSON 解码发生在主线程**。且 DataStore 是整份 Preferences 一起发射、这些 flow 均无 `distinctUntilChanged` → **改一次主题色就会把 items/archive/consumption/history/thresholds/categories/locations 全部重新解析一遍并产生新 List 实例**，触发全屏重组。`nutstorePasswordFlow` 每次还会做一次主线程 Keystore AES-GCM 解密。

### 修复设计

统一改写为「先取原始串 → 去重 → 解码 → 切线程」：

```kotlin
private fun <T> rawFlow(key: Preferences.Key<String>, decode: (String?) -> T): Flow<T> =
    context.dataStore.data
        .map { it[key] }
        .distinctUntilChanged()
        .map(decode)
        .flowOn(Dispatchers.Default)

val itemsFlow: Flow<List<FoodItem>> = rawFlow(itemsKey, ::decodeItems)
```

布尔/整型等轻量 key 只加 `distinctUntilChanged()`，无需 `flowOn`。
`nutstorePasswordFlow` 额外加 `flowOn(Dispatchers.Default)`（Keystore 操作）。

> 注意：`AppViewModel.ready`（:107）用 5 个 flow `combine` 做首帧门控，加 `distinctUntilChanged` 后语义不变（首次发射仍会触发）。需回归验证启动无白屏/闪烁。

### 验收

- 冷启动无回退（SplashScreen 门控仍生效）；
- 造 200 条归档 + 500 条消耗流水，连续点数量步进器，观察掉帧改善（Layout Inspector / `dumpsys gfxinfo`）。

### 三条路径

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 抽状态层（推荐）** | 把筛选/聚合/多选/动画时序提为 `rememberXxxState()` 或 VM 派生 StateFlow，两套 UI 只保留纯渲染 | 中等；可逐页进行，风险可控 |

| **C. 维持现状** | 接受双份维护，靠纪律保证同步改动 | 每次业务改动都有"只改了一半"的风险 |

**本阶段不与 1–6 混做**，建议 1–6 落地并稳定后单开议题。
